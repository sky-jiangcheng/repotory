Architecture decision · 2026-10-02 · Distribution

AI won’t distribute for us: letting the plugin meet people

Repotory’s plugin assets had always served agents; not one of them ever appeared in the interface developers keep open. ADR-0009 turns “visibility” into a product-level constraint — one-click registration first, then a VS Code extension, JetBrains deferred.

Repotory ·2 October 2026 ·6 min read ·中文

Assets that go invisible on install

Take stock of Repotory’s distribution assets — the MCP server, the dsh Harness plugin, llms.txt — and every one of them serves an agent. MCP tools only ever appear inside an agent’s chat panel; on the IDE surfaces people actually use — command palette, status bar, sidebar — Repotory does not exist. Install it and it disappears.

That blind spot imposes two hard limits on adoption. First, agents will not discover our plugin for us: nothing makes a new user’s AI agent say “you should install repotory-mcp” — distribution has to be done by a person, and people only discover tools in interfaces they open every day. Second, word of mouth needs a visible shelf: when someone asks “what do you use to keep project memory?”, and the answer is a server that vanishes on install, the chain breaks at step one.

Agents will not install plugins for us — visibility is a cost the product has to pay itself.
·  ·  ·

The capability isn’t missing; the introduction is

To be clear, this is not a capability gap. VS Code (Copilot Chat) and JetBrains (AI Assistant / built-in MCP client) both support MCP registration natively, and the setup docs already spell out the manual path. There are exactly two gaps. One is setup friction — a new user has to hand-edit .mcp.json. The other is zero “human” experience inside the IDE — no Repotory: Handoff in the command palette, no “last handoff” in the status bar, no note search in the sidebar.

In other words, the tool capability is available in both IDE families today; what is missing is the introduction, not the feature.

·  ·  ·

The decision: one-click registration first, then one extension

ADR-0009’s path has three steps. Step one, already shipped, is one-click registration: repotory-init probes for the repotory-mcp binary, writes the registration into Claude Code, Cursor, VS Code and Windsurf, and optionally installs an end-of-session auto-handoff hook:

node scripts/repotory-init/index.mjs --with-hook

Step two is a VS Code extension — and the only IDE extension: three command-palette commands (context / handoff / search), the status bar showing when the last handoff happened, note search in the sidebar that jumps to the file, and first-run guidance that registers with one click. Step three is the thin-client discipline every new asset obeys: MCP stays the single execution interface, internal/service stays the single source of truth, and the extension is a thin shell with zero duplicated logic — the same pattern as the dsh plugin.

·  ·  ·

Why not an IDEA plugin

VS Code first is arithmetic, not preference: one VSIX covers the whole VS Code / Cursor / Windsurf fork family — the only shape that is “one investment, meet the whole family” — while one JetBrains build covers one vendor and needs a separate Kotlin / Gradle code base, which doubles the maintenance surface outright. Until there is a real demand signal (an issue, a star) and an ADR arguing for it, it is not started and no code is written.

This trade-off also reconciles the scope freeze (ADR-0006): what was frozen is platform infrastructure — the plugin SPI, the HTTP server, multi-backend storage — not the distribution surfaces that meet people. The thin-client discipline keeps new assets evolving only with the public API, so maintenance stays bounded.

·  ·  ·

A new bar for starting work

ADR-0009 also leaves a long-term principle: a distribution evaluation gate. Every future distribution asset must answer, when it is proposed, “on which interface does a person see it?” An asset only an agent can consume, and no person can see, has to say whether it serves depth for existing users or acquisition. Visibility is no longer a marketing question; it is a cost the product has to pay itself.

Step one has shipped.
