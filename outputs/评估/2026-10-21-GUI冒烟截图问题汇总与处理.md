### #5 首页计数占位符泄漏 ✅（本轮新发现，上一轮修得不彻底）

| | |
|---|---|
| 现象 | 首页显示「(count) 个项目」，不是「33 个项目」 |
| 根因 | 上轮修 #5 时新加的三个 locale key 用了**单花括号** `{count}`。i18next 的插值语法是**双花括号** `{{count}}`；单花括号不报错、不告警、`tsc` 与 `eslint` 都看不出来，i18next 把它当普通文本原样吐出 |
| 波及 | `home.projectCount`、`home.projectCountWithRepos`、`home.projectCardsTruncated`、`knowledge.organizeJump`（zh + en 共 6 处） |
| 修复后 | 「仅显示 3 / 33 个重点项目」、「待整理 17」（截图 `07-home-i18n-fixed.png`） |

**这类错误必须有守卫防复发** —— 它不在任何断言的失败路径上，只能靠人眼在界面上看见。新增：

- `scripts/check-i18n-interpolation.mjs`：两条检查
  1. **单花括号占位符**：值里出现 `{ident}` 且不属于 `{{...}}` → 报错
  2. **占位符孤儿**：locale 声明了 `{{name}}` 但源码里找不到同名传参 → 报错（防改名后留下的死占位符）
- `.github/workflows/ci.yml` 新增 `i18n-interpolation` job（纯 node、零依赖，与 `docs-mirror` 同形）
- **反向验证**：注入 `{count} 个项目` 与 `共 {{ghostCount}} 项` 后脚本 exit 1 并精确报出两处；恢复后通过 —— 确认它不是永远绿的摆设。

## 二、本轮修掉的连带回归（由 #6 与 #5 的改动暴露）

这三个都是**上一轮的修复自己引入的**，且都不在原修复的验收范围内 —— 记录在此，因为它们揭示了同一类风险模式。

### 排序翻转导致 `compileNoteTargets` 取到最旧的笔记 ✅

`internal/db/notes.go` 的 `ListNotes` 从 `created_at ASC` 改为 `updated_at DESC` 后，`compileNoteTargets`（原为**反向**遍历，依赖「列表是最旧在前」）立刻开始编译项目里**最陈旧**的笔记，而不是最新的。

这不是测试断言问题，是**真实行为回归**：知识库编译会静默地编译过期内容。修法是取列表头部（`notes[:limit]`），并在注释里写明它现在依赖「`ListNotes` 是 newest-first」这一前提。

### 排序翻转让 W2 检索门禁的基线失去意义 ✅

`wiki_evidence_test.go` 的 `legacyNoteIDs` 复现「pre-W2 行为 = 塞进最旧的 10 条笔记」，但它取的是 `ListNotes` 的**头部**。排序翻转后头部变成了**最新** 10 条 —— 基线不再衡量「 stuffing 旧笔记」，而是衡量「 stuffing 新笔记」，门禁数字失去意义。修法：helper 内显式按 `created_at ASC, id ASC` 排序，与 `ListNotes` 的方向解耦，把基线钉回它文档化的语义。

### 排序翻转让 queryset 工作表的编号断言失真 ✅

`cmd/queryset/main_test.go` 断言「行号 1 = 最先创建的笔记」，而工作表的编号直接来自 `ListNotes` 顺序。真实契约是**「行号 N 解析到工作表第 N 行的那个 id」** —— 用户是看着工作表填数字的，不是看着创建顺序。改为从工作表文本解析出该行号的 id 再断言，使测试与排序方向解耦；并加了一条「若两条 fixture 笔记共享 id 则此断言无意义」的自检。

> **风险模式小结**：翻转一个被广泛共享的列表顺序，隐藏依赖不会在编译期暴露，只会在下游「恰好反过来遍历」的地方变成静默的行为错误。已全量核查 `db.ListNotes` 的 6 个调用点：`note.go` 纯透传、`ai.go` 注释本就声明 newest-first、`wiki_compile*.go` 与 `queryset` 已修。
