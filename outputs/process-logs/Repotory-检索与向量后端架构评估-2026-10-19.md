## 1. Pinecone / Milvus：注册表加法（可选配置已就绪）

### 现状（代码证据）

- `internal/search/vectordb/store.go`：`Store` 接口（`Ensure/Clear/Upsert/Search`）+ `Register(kind, factory)` 注册表，`Open(database, kind, url, apiKey, collection)` 按 `vector_store`(local|qdrant|weaviate|chromem) 选择；**选了远程但不可达 → 静默退回本地 sqlite-vec**（fallback 语义已定型并有测试）。
- 配置四键已在白名单：`vector_store` / `vector_store_url` / `vector_store_api_key`（secret，GetConfig 打码）/ `vector_store_collection`（`internal/service/config.go:48-51`）。
- 已实现三后端：Qdrant（REST，真容器冒烟通过）、Weaviate（REST）、chromem-go v0.7.0（嵌入式纯 Go，强制持久化目录、拒绝内存态）。ADR-0013 候选矩阵原话：「再换 Pinecone/Milvus 只需再加一个 `Store` 实现（按真实 API 核验后再写，勿凭记忆）」。
- 唯一调用方：`service/search_semantic.go:81`（经 memo 失效路径），消费端零改动。

### 评估

- **工程成本（每后端）**：一个 `Store` 实现（REST 与 qdrant.go 同模式）+ 注册一项 + 手册配置表 + build-tag 门控的真服务冒烟测试（`qdrant_live_test.go` 模式）。量级：1–2 天/后端，不含联调。
- **Milvus 先于 Pinecone 的理由**：Milvus 可**自托管**（Docker，正是 v2.8.0 刚交付的部署档语义）——向量与查询向量不出内网；Pinecone 是纯云 SaaS，构成**第二个外发点**（embedding 已按 `semantic_search` 门出端点，向量入库是另一跳）。若做 Pinecone，隐私门建议并入 `semantic_search`（同一授权语义「同意文本发给端点」），但手册必须写明数据流向两级。
- **共同工程项**（两后端同）：`page_embed_dirty` 排空器适配（按 store 路由或双写，**不得**破坏 ADR-0015「只嵌 approved 页」边界）；删除/撤销 approved 的传播；`abeval` 平价门——**切换 store 不得劣化既有 delta**（与 M3 同一标注集复跑）。
- **诚实预期**：本地 sqlite-vec 在个人库规模（当前数百向量，百万级才到 sqlite-vec 的舒适区之外）零网络往返、零运维；远程后端的价值只在 ①库规模 >5 万向量或延迟可感、②多端共享索引、③用户明确要云端语义检索。**三者今天均不成立。**

### 建议动作

不写代码。触发条件任一出现时，按上述清单落地；顺序 Milvus → Pinecone。`lancedb` 因 CGO 破零 CGO 红线，**明确不接**（注册表注释已记）。

## 2. Bleve：先度量，再谈「可选」（不建议直接做运行时切换）

### 现状（代码证据）

- FTS **不走** `Store` 接缝：FTS5 是 `db/search.go` 直写 SQL + `project_notes` 上的触发器同步 + `hybrid.FuseRRF` 的 lexical 臂 + `evidencePages` 的「关图时逐条一致」契约——四处耦合。
- v2.2.0 已修复 CJK 词法不可达（纯 CJK run 切重叠 3-rune trigram + OR 松弛 + LIKE 回退 + `julianday` NULL 兜底）；真库 51 条人工标注 query 上 lexical recall@10 = **0.608**，hybrid = 0.735（delta +0.127，k=3..50 全区间 PASS）。
- Bleve（纯 Go）不在 go.mod；注册表注释预留了 `"bleve"` 位（store.go:35），ADR-0013 矩阵标注「可连 FTS5 一起替代（大改动），1M 规模边际」。

### 评估

- **「多选项」在文本检索层的真实代价**：双引擎 = ①每次笔记写入双写（FTS 靠触发器，Bleve 得 Go 侧维护或影子表）；②删除/更新传播的一致性面；③每个消费点（MCP 搜索、hybrid、evidence）都要引擎分叉与「谁作答」的语义裁决；④索引存储翻倍。这些成本**每天都在付**，而收益是未知的。
- **收益是可测量的**：`internal/search/abeval` + 51 条标注集 + `Compare` delta 门就是为此存在的度量设施。正确顺序是**先量测后决策**——写一个一次性 bench（建议 `.annotation-prep/bleve-ab/` 脚本 + 临时 cmd，**非产品代码**）：同库同标注集，Bleve cjk bigram 分析器 vs 现有 trigram+OR 路径，跑同一 GATE。
- **判定阈值建议**：recall@10 增益 ≥ **+0.05**（与 M3 门同量级）才值得立项；否则关闭此线（trigram 修复后 lexical 基线已 0.608，Bleve 的 dictionary-free bigram 对 CJK 的边际空间有限；其真实卖点——英文词干化、高亮——与本库当前 query 形态关系不大）。
- **若将来立项**：形态尊重「可选配置代替替换」——`search_engine: fts5|bleve`（默认 fts5），Bleve 索引落数据目录文件（非库内表，迁移不动 schema）、懒构建 + 可重建；产品语义仍是「切换实验门」，长期是否收敛到单一引擎由数据定。

### 建议动作

不替换、暂不做运行时切换、不在 go.mod 引入 bleve。度量本身也**等有真实痛点再跑**（当前无证据表明 lexical 是短板——短板在图密度，见 lane 2 条件 10）。

## 3. OMP 导入：协议版本赌注，维持等 v1

### 现状（代码证据）

- `internal/service/omp_export.go`：OMP v0.4 兼容导出，头注明 **PROVISIONAL**（超集投影、非稳定契约）；**导入侧有意未写**（ADR-0013 outlook）。
- 已有的互操作面：`ExportMemoryJSON`（自有全量格式）+ `GenerateLLMsTxt`——「多选项」在导出层已成立。

### 评估

- 导入器对一个 pre-1.0 协议落码 = 把**外部 schema 漂移**引到**用户数据面**（笔记入库），这正是 ADR-0011「不背未公开易碎格式长期债」纪律要拦的事。等 v1 不是拖延，是唯一正确姿势。
- **v1 稳定后的落地形态**（预先定型）：
  1. `omp_import_enabled` 配置键 opt-in（默认关，延续隐私门纪律——导入即外部数据写入用户库）；
  2. 解析器**版本钉死**：`schema_version` 不认识即拒绝并说明（同 integrity/checks 的守卫风格），不做宽容猜测；
  3. 落点走 **ADR-0023 整理占位流**：`source='omp'`、幂等键 `(project, source, title)`、匹配不到项目落「未分类」/占位，人审归口——复用现成机制，零新面；
  4. 手册写明「OMP 导入是快照搬运，不是持续同步」（持续同步是另一个 ADR）。
