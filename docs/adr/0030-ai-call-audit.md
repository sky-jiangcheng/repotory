# ADR-0030: AI 调用审计——把「谁把什么发了出去」变成可查的事实

- 状态：Accepted（**2026-10-25 落码**。schema v28 新增 `ai_call_log` 表 + append-only 守卫；审查钩子插在 `internal/service/ai.go` 三个 HTTP 原语之前；配置默认全关）
- 日期：2026-10-25
- 关联：[ADR-0002](0002-c-end-repositioning.md)（C 端重新定位——本 ADR 是它的一个**附加能力**，不改定位）、[ADR-0006](0006-scope-freeze.md)（范围冻结——本 ADR 明确声明不扩产品边界）、[ADR-0021](0021-temporal-graph-page-versions.md)（append-only 留痕范式——`ai_call_log` 照抄其「唯一写入者 + 防篡改触发器 + 无外键」结构）、[ADR-0029](0029-in-app-update-download.md)（同期的「信任面」论证风格）
- 起点 schema：v27 → v28（本 ADR 有一处 schema 变更）
- 用户原始诉求（2026-10-25）：「我们的应用是否可以做 AI 内容门控和审查……如果公司所有对外 ai 调用的出口和入口都经过我们的 Repotory，那 ai 使用痕迹是不是已经可控了，如果进行关键词屏蔽和控制，是否就有了集团级别的 ai 使用门控了」

## 背景

一个自然的想法：AI 调用的痕迹若都过 Repotory，就能在出口处做内容门控与关键词屏蔽，从而获得「AI 使用可管控」的能力。

先把能核实的部分核实一遍（这些是本 ADR 的事实基础，全部来自代码）：

**1. LLM 出口高度收敛。** 全仓对外部大模型的 HTTP 出口只有三个原语：

- `internal/service/ai.go:244` `aiGet` —— `GET /models` 探测
- `internal/service/ai.go:270` `aiPostJSON` —— 非流式 `POST /chat/completions`
- `internal/service/ai.go:305` `aiPostJSONStream` —— 流式 `POST /chat/completions`

八条业务路径全部经由 `testAIChatWithTimeout` / `streamChatWithTimeout` 汇聚到这三个原语：`AskAI`（`ai.go:578`）、`AskAIWithEvidence`（`wiki_evidence.go:592`）、`AskAIWithEvidenceStream`（`wiki_evidence.go:621`）、`askCompilePlan`（`wiki_compile.go:210`）、`askMergeBatch`（`wiki_merge.go:613`）、`askCommunitySummary`（`wiki_community.go:446`）、`runWikiLintLLM`（`wiki_lint.go:430`）、`OrganizeNote`（`note_organize.go:60`）。**没有旁路**——这意味着在原语处插一道闸就覆盖全部 LLM 流量。

**2. `internal/service` 是三端共同依赖的唯一业务层。** 桌面端（`main.go`）、headless server（`cmd/server/main.go`）、MCP server（`cmd/mcp/main.go`）都走它，所以一份策略代码天然同时服务三种形态。

**3. 但「痕迹可控」的前提目前不成立。** prompt / response **完全不落库**（`compile_jobs` 只记计数不记内容），也没有任何 audit / activity / call_log 表。更根本的是**没有身份**：`internal/httpapi/server.go:10` 明写 *"this API has NO authentication"*，`cmd/server/main.go:117` 把监听地址硬编码为 `127.0.0.1`，库里没有 user / tenant 表。所以就算记下「某时刻有人调了某模型发了这些内容」，也不知道**是谁**。

**4. 「集团级」的前提不由 Repotory 决定。** 要覆盖全公司的 AI 调用，需要流量**必须**经过 Repotory——那是网络层与身份体系的职责，不是本地应用能保证的。

## 决策

**1. 这是安全插件，不是产品升级，也不另立产品。**

三种形态的比较：

| 形态 | 做法 | 对现有价值锚点的影响 | 判定 |
|---|---|---|---|
| 产品升级 | Repotory 变成「公司 AI 网关」 | **锚点被覆盖** | 否决 |
| **安全插件（本决策）** | 记忆层仍是主角，合规是可开关的附加能力 | **锚点不变** | **采纳** |
| 独立网关产品 | 另起项目做集团 AI 出口 | 锚点清晰但工程量与 Repotory 体量严重不匹配 | 否决（且真到那一步共同代码趋近于零，不该同仓） |

否决「产品升级」的理由是气质冲突，不是工程量。README 的定位是 *"The local-first memory layer for AI coding agents"* / *"Local-first, no cloud, no account. One SQLite file on your disk."*。而「集团合规门控」的内在诉求是**反向**的——要有身份、要有中心策略、要能管别人。**私有资产越私密越有价值，公共设施越中心化越有价值**，两者强行合并的结果是私有用户觉得被监视、企业用户觉得不够合规。

否决「独立网关」的理由是能力缺口：`cmd/server` 目前是「本地 agent」而非「中心服务」（`docker-compose.yml:5` 明写 *"The API has no authentication and must not be exposed to the public internet directly; put it behind an authenticating proxy"*），SQLite 是单写者嵌入式库（`internal/db/db.go:23` `SetMaxOpenConns(1)`）。集团网关需要身份体系、多租户、共享数据库、中心策略分发、审计归集——那是**另一个产品的工作量**，不是另一个模块的工作量。

**2. 定位三层必须分开：记忆层 / AI 审计 / 未来的网关。**

- **记忆层**（主角）：本机私有、跨 Agent 共享知识、人审后入库。**本 ADR 不改变它的任何一条承诺。**
- **AI 审计**（本 ADR）：一个**默认关闭**的附加能力，落在知识与模型之间。
- **网关**（未来，若有）：中心化、需要身份的另一件事。**本 ADR 明确不承诺它**，也不为其预留实现。

判据写在这里以便日后自查：**新增能力若让「记忆层」这一定义失效，就必须另立产品**。按此判据，审计插件通过（它只是让已有的出口多一道可选闸），而「Repotory 变成公司网关」不通过。

**3. 插件形态的硬约束：不破坏「本机私有」承诺。**

具体化为四条：

- **默认全关。** 三个配置键（留痕开关、输入审查、输出审查）默认值均为关。关闭时行为与今天**逐字节一致**——已有用户零感知。
- **不引入账号。** 单机版不需要任何身份。「身份」是部署版的扩展点，不是本 ADR 的实现内容。
- **留痕默认只存哈希 + 元数据，不存全文。** 把 prompt 全文写进本地库会污染知识库并把密钥带进数据库，这与「本机私有」背道而驰。默认记录的是「发生了什么」的证据（时间、端点、模型、调用面、prompt 哈希、token 数、判定结果），而不是「说了什么」的全文。**存全文是一个需要显式开启的选项，且开启时必须同时说明它会写入知识库。**
- **不新增对外网络出口。** 审计数据只落本地 SQLite，绝不外发。

**4. 审查插在三个 HTTP 原语之前，且流式路径必须单独处理。**

- 输入审查在 `aiPostJSON` / `aiPostJSONStream` 构造请求**之前**执行，命中即阻断，不发出请求。
- 输出审查在 `aiPostJSONStream` 的 SSE 解析处做**增量**检查：`parseSSEStream`（`ai.go:351`）是逐 chunk 交付 `onDelta` 的纯函数，因此可以在 chunk 边界判断，但**已交付给前端的 chunk 无法撤回**——这是流式审查的固有代价，必须在实现中如实对待（见「实现修正」）。
- `aiGet`（`/models` 探测）不携带 prompt，只做 URL 策略检查，不做内容审查。

**5. 留痕表是 append-only，且照抄 ADR-0021 的结构。**

`ai_call_log` 沿用 `page_versions` 已论证过的三条结构决策：**唯一写入者 + append-only 触发器守卫 + 无外键**。无外键的理由在 ADR-0021 里写得很清楚且同样适用：SQLite 会为外键 CASCADE 动作触发行触发器，带级联外键的 append-only 表会导致「删掉被记录的对象」直接失败——而一条会随对象消失的审计行不是审计行。

**6. 与 skill 机制划清边界。**

两个机制方向相反，必须在同一份文档里说清，否则日后必然职责重叠：

- **skill 机制**（ADR-0007 会话记忆协议 + `skill/repotory`）= 入口侧，Agent 主动**读**知识。
- **AI 审计**（本 ADR）= 出口侧，数据**出**本机时的管控。

它们是互补的：**记忆层鼓励 Agent 多读，审计层保证读到的敏感内容不会被带出去。** 组合起来正好补上当前 AI 编码工具最缺的一环——既能跨会话记忆，又不泄露。

**7. 关键词屏蔽被明确定位为「弱控制」，不作为主要卖点。**

关键词/模式匹配在工程上简单，在效果上脆弱：绕过成本极低（改写、拆词、编码），误报代价高（内部系统名、正常业务词被拦会立刻引发绕开意愿），且它**挡不住真正的泄露路径**——真实风险是 prompt 里带出了客户数据、源码、密钥，而这些往往不含任何关键词。

因此本 ADR 的定位是**「自证清白 + 早期预警」**，不是「防泄露」。真正强制的门控需要服务端部署与身份归属，属于未来网关的范畴。

## 候选矩阵（这个能力做成什么形态）

| 方案 | 价值 | 主要风险 | 判定 |
|---|---|---|---|
| **安全插件，默认关**（本决策） | 锚点不变；独立价值；已有用户零感知 | 单机版无法自证（无身份），这是明说的边界 | **采纳** |
| 产品升级为「公司 AI 网关」 | 理论上覆盖最全 | 锚点被覆盖；气质冲突；已有用户被劝退 | 否决 |
| 独立网关产品 | 集团级能力完整 | 工程量与体量不匹配；共同代码趋近于零 | 否决 |
| 完全不做 | 零风险 | 放弃了唯一天然收口点；AI 调用仍是黑盒 | 否决 |

## 后果

**正面**：

- AI 调用从黑盒变成可查事实，且是**本机可查**——不需要连任何中心服务。
- 三个原语单一收口的性质得到兑现：闸门只插一次，覆盖全部八条业务路径与三种运行形态。
- 定位边界被文档钉死，日后若有人提议「把 Repotory 变成公司网关」，有明确的判据可以反驳。

**负面（不粉饰）**：

- **单机版的审计证明力有限。** 没有身份，「谁调的」只能是本机视角的回答。这是本 ADR 明确接受的边界，不是待修的 bug。
- 关键词审查有误报与漏报双向问题，用户可能觉得「拦得不对」。默认关闭正是为了让用户在自己判断规则合适后再开。
- 流式输出审查无法撤回已交付的 chunk，**只能截断后续内容**。
- 启用全文留痕会把 AI 交互内容写进知识库，与笔记、页面混在同一库里——这是本 ADR 明确要求在开启时告知用户的代价。

## 实现修正（落码与设计不同的事实）

1. **`ai_call_log` 的写入方是 service 层而非触发器。** ADR-0021 的 `page_versions` 用触发器是因为「所有写入路径都经过 internal/db」；而 AI 调用留痕的触发点是 `internal/service/ai.go` 里的 HTTP 原语——它不在 db 层，触发器无从挂载。因此这里由 service 层显式写入 append-only 表，append-only 仍由**表上的 BEFORE UPDATE / BEFORE DELETE 触发器**保证。差别是：写入方不是触发器，而是「唯一调用原语」这个事实保证的——三条业务路径全部经过 `aiPostJSON` / `aiPostJSONStream` / `aiGet`，没有第二条路。
2. **prompt 哈希用 SHA-256 而不是摘要文本。** 摘要文本需要额外存原文才能计算，等于把全文又存了一遍。哈希可回答「是不是同一份 prompt」而不可回答「内容是什么」——这正是默认档位想要的。
3. **调用面（surface）靠上下文显式传入。** 原语本身不知道调用来自 MCP、HTTP 还是桌面，因此由各调用面在进入原语前设置。默认值取 `unknown` 而非猜一个。
4. **流式输出审查在 chunk 边界判断，命中即停止继续交付**（`onDelta` 后续不再被调用），并把已交付的部分标记为不完整——因为此时已经无法撤回。
