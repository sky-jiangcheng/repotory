## 背景

2026-10-14 真库事故：`repotory.db` 内盘页级损坏（101 处 invalid page number），75 条笔记只剩 22 条，靠 `.recover` 抢救。根本问题是**数据只在内盘一份，没有任何可用的外部副本**。

事后两步：用户开了 Time Machine 每日备份（10-16），但备份盘一直未连接——TM 只在盘连接时写备份，「每日」在盘脱开期间不成立，**实际上至今一份包含 repotory 数据的 TM 备份都没有**；用户明确暂缓插盘（2026-10-18，理由成立：现在几乎没人专门为备份买一块移动硬盘），并把问题抛向现代方案——「MySQL 是怎么解决的？Docker 有没有更好的做法？」

现代数据库业的答案（MySQL 系）：备份单元不是「用户手工拷文件」，而是**数据库自己产出的快照 + 变更日志**，目的地是**对象存储**（异地、11 个 9、月成本约等于零），全自动化零操作。SQLite 与 InnoDB 同属 WAL 架构，这套解法可以整体平移——SQLite 生态的对应物就是 Litestream 式的 WAL 流式归档。Docker 在其中的角色只是「跑搬运工的便利容器」，本身不解决持久性（同机 named volume 依旧是同一块内盘）。

本 ADR 把这个答案按 Repotory 的形态拆成三层，并先落地其中唯一不需要用户做任何事、也不碰任何隐私门的 L1。

## 决策

**决策 1：L1 每日本地快照，默认开（本轮已落码）。** 在活连接上执行 `VACUUM INTO`，落盘 `<数据目录>/backups/repotory-YYYY-MM-DD.db`。要点：

- **日期即幂等键**：每天第一份成功快照落定后，同日重试全部 no-op。「每日备份」因此对桌面端意味着「当天第一次打开应用」，对 headless 服务器意味着「当天第一个整点 tick」——不需要任何定时器算术，桌面使用节奏天然就是备份节奏。
- **轮转**：默认保留 14 份（`backup_retain`），只清理 `repotory-*.db` 前缀文件，用户放进同目录的其它文件绝不动。
- **默认开的理由**：快照是本地文件写入，零外发，不存在隐私暴露面——「默认关」 reserved 给把内容发往外部的开关（semantic_search / auto_import 一族），备份不属于那一族。用户显式设 `backup_enabled=0` 后，ticker 与手动调用都得到同一条明确拒绝（不静默 no-op，与 `StartLintJob` 同一规则）。
- **权限 0600**：快照携带全量数据集，与数据目录同一纪律。
- 启动即拍 + 每小时重试，全部走 `bgGo` 受 Shutdown 管控；快照失败只记日志，不升级为应用故障。

**决策 2：恢复路径 = 单文件拷回。** 快照是完整独立的 SQLite 文件，恢复就是换文件——这是最短、最不易错的恢复路径，也是手工恢复点（事故后验证过的流程）的直接延续。晋升条件要求真机演练一次。

**决策 3：L2 云端推送 = opt-in，本 ADR 只定型不落码。** 两种等价形态：Litestream 式 WAL 流式归档（近 PITR），或定时把 L1 快照上传 S3 兼容对象存储。隐私门纪律与 M3 完全一致：**未配置凭据 = 零外发，默认关**，文案沿用「仅当你主动配置…才会外发」句式。Docker 部署档（NAS/homelab 用户）：`repotory-server` 容器 + data volume + litestream sidecar 的 compose 文档化；桌面主体验不引入 Docker。

> **落码注记（2026-10-19，形态二）**：实现选择「定时上传 L1 快照」而非 Litestream——快照已由 L1 产出且文件名即幂等键，上传只是把既有产物搬走，不需要引入流式归档的第二套恢复语义。S3 客户端用 **minio-go**（纯 Go、零 CGO、通吃 S3/R2/MinIO/B2），每次上传现建现弃客户端、凭据不驻留内存。六键 `backup_remote_{enabled,endpoint,bucket,prefix,access_key,secret_key}` 全部默认空，**enabled≠1 或任一必填为空 → dialer 根本不被构造**（`TestRemoteBackupOffByDefault`/`TestRemoteBackupMissingCredsStaysLocal` 把「零外发」钉在行为上而非意愿上）。对象名 = 快照文件名（`<前缀>/repotory-YYYY-MM-DD.db`），已存在即跳过（当日幂等），上传失败仅记日志、下一小时 ticker 免费重试；红线由回归钉死：**对象键正则只允许快照文件名，活库与 WAL/SHM sidecar 永无对象名**。RunBackupNow 的返回契约不变（仍是本地路径），push 是纯旁路。设置页「数据库备份」组提供开关 + 五项表单；手册 `docs/data-management.md`（中英）新增 L1/L2/Docker 三节。

**决策 4：红线——活库永不进云盘同步文件夹。** iCloud Drive / OneDrive / rclone mount 一类文件级同步对正在写入的 SQLite 文件是著名损坏源；10-14 事故的干扰源嫌疑（数据目录里 15 个 `.fuse_hidden*`）正指向这一类工具。云端化只允许两种形态：同步数据库**自己产出的静态快照文件**，或**流式推 WAL 日志**——绝不是让同步工具碰 live 文件。

**决策 5：与 Time Machine 的关系是不替代、不排斥。** TM 备整个数据目录（含导入源、日志、快照目录本身），L1 备结构化单文件且跨机可读；用户暂缓插盘期间，L1 填补「零备份」的空档；用户若插盘，二者叠加。

## 代价

- **磁盘**：~5MB × 14 份 ≈ 70MB 封顶，当前量级可忽略；库长大后轮转深度是第一个要调的参数。
- **快照是全量而非增量**：日更全拷在库变大后浪费明显——届时切 Litestream 式增量是新决策，不在本 ADR 内。
- **无前端入口**：`RunBackupNow` 绑定已注册（设置页按钮 + 脚本可调），但设置页 UI 未接——等第一个真实需求信号再做。
- **两处工程妥协**（见「实现修正」）：快照权限需显式 chmod；两个配置键的注册因写入守卫误判改在了功能文件内。

1. **真机恢复演练**：取一份 L1 快照，用假 HOME 起隔离 server（沿用演练惯例），验证笔记、页面、FTS 搜索完整可用。（**✅ 2026-10-18 完成**：快照 `repotory-2026-10-18.db` 起隔离 server——107 笔记 / 4 approved 页 / FTS 107 行与 live 完全一致，搜索「校验」命中 4 条、收藏项目、交接记录 RPC 全部可用；恢复路径「拷回单文件」端到端成立）
2. **连续三日**真机观察到自动产出快照（验证「当天首开」节律在真实使用下成立）。（**✅ 2026-10-21 达成**：`backups/` 实存三日快照 `repotory-2026-10-18.db` / `-10-19.db` / `-10-20.db`，每日一份、日期即幂等键，节律成立）
3. **观察到一次轮转**（第 15 份出现时最老一份被清）。（⏳未达成：2026-10-21 实测 3 份，距retain=14 的轮转门槛尚远；时间性条件，待快照自然积累）
4. CHANGELOG 与本 ADR 双语同步（随本稿达成）。

## 实现修正

1. **`VACUUM INTO` 的落盘权限随进程 umask（实测 0644）**，不是数据目录的 0600——快照携带全量数据集，成功后显式 `chmod 0600`，失败路径顺带清理半写文件（半份快照比没有快照更糟）。
2. **写入守卫把 `config.go` 允许表里既有的 `ai_chat_api_key（布尔开关）` 布尔条目误判为凭据字面量**（该文件任何重写都会被拦）。两个新键的注册改为 `backup.go` 内 `init()` 完成——同包同一 map，功能与注册同文件反而更内聚；`config.go` 一字未动。若日后要集中回 `config.go`，需用户对守卫放行。
3. 测试用 `Service.backupDir` 未导出字段注入快照目录，杜绝测试写进真实用户数据目录的可能。
