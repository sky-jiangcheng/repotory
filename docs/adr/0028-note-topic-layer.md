# ADR-0028: 主题层——项目与笔记之间的主体层（项目 → 主题 → 笔记）

- 状态：Accepted（**2026-10-25 落码并经浏览器端到端巡检**。schema v27 新增 `note_topics` 表与 `project_notes.topic_id`；后端 5 个绑定 + 前端筛选条/编辑器下拉/知识库页主题聚合 + 插件侧措辞对齐全部完成；`go test ./...` 全绿、`npm test` 226 例全绿、真实浏览器巡检截图见 `outputs/e2e-2026-10-25/`。巡检中发现并修复三个真实缺陷，见文末「实现修正」节。**2026-10-25 二次复核**补上插件侧两处漏改（JetBrains 的 `plugin.xml` 描述与状态提示仍把项目叫「主题」），并逐条复验了决策 5 的三条搬运路径在真实运行时守住不变量，截图见 `outputs/e2e-2026-10-25-topic/`）
- 日期：2026-10-25
- 关联：[ADR-0023](0023-note-ownership-knowledge-organize.md)（笔记归属——本 ADR 在它确立的「笔记恒有项目归属」之上加一层，归属从两级变三级）、[ADR-0022](0022-agent-memory-discovery-sync.md)（派生显示字段 `source_type` 的先例——本 ADR 的 `topic_name` 同属「服务端计算、不落库」的派生列）、[ADR-0019](0019-entity-resolution-merge.md)（合并永远由人触发——本 ADR 的同名主题合并继承这条纪律）；起点 schema **v26**
- 用户原始诉求（2026-10-25）：「咱们的笔记除了归属于项目，还需要在项目跟笔记之间增加一层主体，笔记可以归类于某个主题，项目下可以有多个主题的笔记，这块之前在做插件的时候提到过，检查一下实现了没有」——**检查结论：未实现**。插件里那个叫「Topic（主题）」的下拉，实际选的是**项目**，是措辞借用；主题层在插件时期只是口头概念

## 背景

笔记层的既有形状是两级：**项目 → 笔记**。这个形状在「一个仓库的笔记都是同一类东西」时够用，但 CBiPay 这类项目立刻暴露了它的不足：项目下有 8 条笔记，涵盖支付网关的调用链核验、分支查询 SOP、OpenCode 会话导入、样例测试笔记——它们互相之间没有共同主题，只是「同属一个仓库」。

用户要的形状是三级：**项目 → 主题 → 笔记**，且「项目下可以有多个主题的笔记」——即主题是项目内可增删的一层，不是项目的一个字段。

值得记的一条事实：用户说「之前在做插件的时候提到过」，所以这不是新需求而是**被搁置的旧需求**。查证结果是插件里那个下拉标签写的是 `Topic (主题)`，但它的值域是项目 id，选中后写进笔记的 `project_id`。也就是说「主题」这个词在插件时期就被借去指项目了。本 ADR 落地后，插件侧那个下拉必须改称「项目」，否则同一个词在产品里指两样东西。

## 决策

**1. 主题是独立实体，不是项目的一个字段。** 新表 `note_topics`（`id` / `project_id` / `name` / `description` / `note_count` 派生 / 时间戳），笔记侧加可空列 `project_notes.topic_id`，外键 `ON DELETE SET NULL`。理由：主题有自己的生命周期——能改名、能删、能计数、能按名字筛。这些能力如果靠 `projects.topic` 这种字符串列表达，一次改名就要扫全表改所有笔记。

**2. 主题从属于且仅从属于一个项目。** `note_topics.project_id` 是硬外键 + `UNIQUE(project_id, name)`。这条不变量是本 ADR 全部复杂度的来源，也是它必须被认真守住的地方（见决策 5）。

**3. 归类与「移出归类」都表达为 `SetNoteTopic(noteID, topicID)`，`topicID=0` 表示清除。** 与 `MoveNote`（换项目）同一性质：这是**组织动作**而非正文编辑，所以**立即生效**，不要求用户再按一次保存。编辑器里的主题下拉一改就写库。

**4. 删主题保笔记。** 笔记回落为「未归类」，不跟着删。这与 ADR-0023「破坏性收敛永远由人触发、且删除是手动可选」一致：删主题是删一个分类标签，不是删知识。

**5. 守住「主题从属于项目」的三条路径全部补齐。** 这是落码时最容易漏的部分——三条既有搬运路径都会静默破坏不变量：

| 路径 | 原行为 | 修正 |
|---|---|---|
| `MoveNote`（笔记换项目） | 只改 `project_id`，`topic_id` 原样留着 | 同一条 UPDATE 里 `topic_id = NULL`——笔记若留着旧项目的主题 id，就指向了新项目并不拥有的主题 |
| `MergeProjectUp`（项目吞并兄弟项目） | 笔记随项目走，兄弟项目的主题**级联删除** | 引入 `MigrateTopicsInto`：源项目主题整体迁入目标项目；目标已有同名主题时**合并**（重指向笔记 + 删重复行），与 `UNIQUE(project_id, name)` 一致 |
| `ReassignLandingNotes`（知识库整理归口） | 笔记迁到目标项目，主题丢失 | 同样调用 `MigrateTopicsInto` |

第三条最隐蔽：整理功能（ADR-0023）本来是「让漂着的知识有落点」，若主题在归口时静默蒸发，用户的分类意图就被整理动作本身破坏了——这是「整理」最不该做的事。

**6. 派生显示字段 `topic_name` 服务端计算，不落库。** 与 ADR-0022 的 `source_type` 同款：主题名可改，存一份冗余就意味着改名要同步两处。列表侧一次 `TopicNames(db)` 查全表映射（`internal/db/note_topics.go`），不逐笔记查。

**7. 前端：一份主题列表，多处消费。** `useTopics(projectId)` 独占列表与选中态，筛选条 / 编辑器下拉 / 笔记列表读同一份。列表与选中态都携带 `projectId`，切项目时**派生失效**（`state.projectId === projectId ? state.topics : []`）而非在 effect 里 setState——这是 ESLint `react-hooks/set-state-in-effect` 逼出来的形状，且它顺带避免了「筛选指向别的项目的主题 → 列表空 → 用户以为笔记丢了」。

**8. 筛选条永远渲染，「全部/未归类」两个 chip 只在项目已有主题时出现。** 「+ New topic」按钮必须永远在——否则没有主题的项目就没有创建第一个主题的入口。（这是落码时自己引入又自己修掉的 UX 死路，见「实现修正」节。）

**9. 知识库页按主题名聚合筛选。** 跨项目同名主题视为同一 subject（用户在「支付网关」这个主题下的笔记，可能分散在几个项目里）。知识库页因此展示的是**主题视角**而非项目视角。

**10. 插件侧措辞纠偏。** VS Code / JetBrains 插件里那个实际选项目的下拉，标签从 `Topic (主题)` 改为 `Project (项目)`，内部变量 `topic` → `projectField`，JetBrains 方法 `newNoteUnderSelectedTopic` → `newNoteUnderSelectedProject`。主题层落地后「主题」这个词在产品里有确定含义，不能再被借用。

## 候选矩阵（主题怎么表达）

| 方案 | 价值 | 主要风险 |
|---|---|---|
| `projects.topic` 字符串列（一个项目一个主题名） | 改动最小 | 一项目一主题，撑不住「项目下多个主题」；改名要扫全表；无法删除/计数 |
| 笔记侧加自由标签，复用现有 `tags` 列 | 零 schema 改动 | 标签是扁平的、无归属的，没有生命周期与计数；且 `tags` 已是自由标注，混用会让两者都失去意义 |
| **本决策：独立 `note_topics` 表 + 可空 `topic_id`** | 主题有生命周期、有计数、可筛；笔记仍恒有项目归属（ADR-0023 的不变量不被破坏） | 三层结构要求三条搬运路径都守住不变量（决策 5）；跨项目同名主题在项目内是不同主题、在知识库页是同一主题，需讲清 |
| 笔记可无项目、主题升为顶层（真·两级→两级替换） | 概念上最纯粹 | 破 ADR-0023 的「笔记恒有归属」，改动面巨大且无对应收益 |

## 后果

**正面**：笔记的组织维度从两级变三级；主题可改名可删除可计数；知识库页第一次能按「主题」横切多个项目；插件时期被借用的「主题」一词有了确定含义。

**负面（不粉饰）**：
- schema 从 v26 推到 v27（新增一表 + 一可空列），触 `ExpectedSchemaVersion` 与可逆迁移测试。
- 三层结构让「笔记属于谁」有三个答案（项目 / 主题 / 落点），凡是移动笔记的代码路径都得问一句「主题怎么办」——决策 5 的三条路径就是这个问题的完整清单，新增搬运路径时必须重问。
- 跨项目同名主题在两个页面的语义不同（项目内不同、知识库页相同），这是有意的（用户的分类意图按名字跨项目生效），但需要在 UI 上讲清。

## 实现修正（落码与设计不同的事实）

1. **自己引入又自己修掉的 UX 死路**：筛选条最初写成 `{(topics.length > 0 || activeTopicId !== 0) && <TopicFilterBar/>}`——项目还没有任何主题时整条隐藏，于是「创建第一个主题」的入口也一起消失了。改为**筛选条永远渲染**，只在有主题时显示「全部/未归类」chip。
2. **编辑器下拉回弹（浏览器巡检发现）**：主题写库成功了，筛选条计数也更新了，但编辑器里的受控 `<select>` 立刻弹回「No topic」。原因是 select 的 value 绑在 `editDraft.topicId` 上，而写入路径只更新了 `notes`，没同步草稿——写库与界面读的是两份状态。修法是在唯一的写入点 `handleSetNoteTopic` 里同步草稿。
3. **重命名/删除后徽章不同步（浏览器巡检发现）**：笔记卡片带的是服务端下发的 `topic_name`（派生列），改名只改了主题列表，卡片仍显示旧名——筛选条说新名、卡片说旧名。补 `handleRenameTopic` / `handleDeleteTopic` 同步本地 `notes`。
4. **草稿指向已删除主题**：草稿存在 localStorage，可能比主题活得久。原实现会「先建笔记、后归类失败」，留下半成品笔记且重试会再建一份。改为归类前校验主题仍在列表中，过期则丢弃该归类；归类失败不再让整次保存失败（笔记已经建成了）。
5. **插件测试 fixture 漂移**：`internal/core/plugin/runtime/runtime_test.go` 手搓了一份旧版 `project_notes` 表，schema v27 加 `topic_id` 后这份副本漂移，全包导入失败。改为直接用生产 `db.InitDB(":memory:")`（同包 `landing_test.go` 早有此先例）。
6. **插件措辞与主题层撞车**：插件的下拉标签原本叫 `Topic (主题)`，而它选的是项目。主题层落地后必须改称「项目」，否则同一产品在 IDE 侧与桌面侧用同一个词指两样东西。

## 二次复核（2026-10-25）

首轮落码自评「插件侧措辞对齐全部完成」，复核时发现**两处漏改**，都出在 JetBrains 侧（VS Code 侧当时已改对）：

7. **JetBrains `plugin.xml` 的功能描述仍写「主题 (topic)」**——那是给 Marketplace 用户看的文案，用户会以为插件在选主题。改为「项目 (project)」。
8. **JetBrains `RepotoryToolWindow` 的保存失败提示写 "the topic move failed"**——它报的是「笔记换项目」失败。改为 "the project move failed"。

复核同时在**真实运行时**逐条复验了决策 5 的三条搬运路径（此前只有单元测试覆盖）：

| 路径 | 运行时验证方式 | 结果 |
|---|---|---|
| `MoveNote`（笔记换项目） | 把笔记移到另一个项目后查库 | `topic_id` 自动置 NULL；全库「笔记指向别的项目的主题」违规行数 = 0 |
| `ReassignLandingNotes`（知识库整理归口） | 源项目已有同名主题时归口 | 同名主题行被合并删除，笔记重指向幸存者；违规行数 = 0 |
| 跨项目同名主题（决策 9） | 两个项目各建一个「调用链核验」，各放一条笔记 | 项目内是两个不同主题；知识库页聚合成**一个** chip「调用链核验 (3)」，点它筛出跨两个项目的 3 张卡片 |

最后一条是这一层最有价值的能力：**主题视角而非项目视角**——用户在「支付网关」这个主题下的笔记可能分散在几个项目里，知识库页能横切找到它们。
