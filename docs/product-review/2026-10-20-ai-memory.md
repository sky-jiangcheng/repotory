# ai-memory 拆解与优劣势分析

日期：2026-10-20 ｜ 对象：[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory)（v2.4 文档态，MIT）
参照系：Repotory 的定位与纪律（本地优先、SQLite SSOT、编译-审核-取证闭环、隐私门默认关）
材料：README + docs/ARCHITECTURE.md（官方），未跑二进制——所有「实测」表述转引自其文档，本文不背书。

## 0. 一句话定位

**跨 agent 的会话记忆总线**：一个自托管 Rust 单体服务，用 lifecycle hooks 静默捕获 20+ 编码 agent 的工作流，把会话编译进一份 git 版本化的 markdown wiki（SSOT），并向任意 agent / 任意机器 / 任意队友提供检索、简报注入与「认领一次」的显式交接。

与 Repotory 的关系一句话：**他们做「会话流的跨 agent 总线」，我们做「项目知识的编译-审核-取证闭环」**——重叠面只在 handoff 与记忆导入，主体是互补而非竞争。

## 1. 拆解（五层 + 集成分发）

### 1.1 捕获层
- Claude Code / Codex / Cursor / Gemini CLI 等 20+ harness 的 lifecycle hooks（SessionStart / UserPromptSubmit / PostToolUse / SessionEnd）把事件 JSON `curl` 到 `POST /hook`；agent 热路径**永不阻塞在网络**——本地 spool + detached drain 助手，饱和时服务端 429 而非无限排队。
- 幂等键设计：普通键 30 天过期；`recovery_<55hex>` 键绑定到 session/agent/事件身份，防预领与重放重复；「at-least-once + 完成标记」的收敛语义写得很细。
- **隐私边界是单一入口**：hook router 的 sanitization 是「不可信文本进存储的唯一路径」；后续所有 LLM prompt 都把 repo 文本/observations/wiki 页当不可信数据加围栏。

### 1.2 存储层
- **markdown wiki 是唯一事实源**（git 版本化），SQLite 是**派生索引**（FTS5 + 会话 + observations + handoffs + 审计 + 可选向量），可随时从文件重建。
- SessionEnd 时**规则式**（零 LLM）合成 `sessions/<id>.md` 摘要页 + 打开一条 Handoff 行（claim-once：有 owner、恰好被认领一次），单事务提交。
- bi-temporal-lite：`as_of` 查询、版本过滤搜索；页内 supersession（不删只换代）+ `restore-page`。

### 1.3 整理层
- 零 LLM 路径：会话页本身就是可用产出。
- 配置 LLM 后：`memory_consolidate` 把摘要页改写成 `concepts/` `decisions/` `gotchas/` 多页（prompt 保源语言、 wikilink 互联、前缀缓存友好的稳定块前置）。
- **auto-improve 调度器**：服务端跨项目复审新完成会话，产 proposal → 默认自动经 wiki 写入路径批准；`require_approval=true` 可改为待审；`[auto_improve.eval]` 可挂**可执行 JSON 契约门**（默认关）——LLM 产物要先过项目自带的评测才能入站。
- 升级保护：per-project 水位线让历史会话不被升级自动补扫；per-session claim 防失败无限重试。

### 1.4 检索层
- `memory_query`：FTS5 + 实体匹配 + 链接邻居 RRF 融合；配了 embedder 再加一路向量 cosine 进同一 RRF。
- 排序修饰：canonical kind / tier / pinned / frontmatter 标签的「权威乘数」——规则/决策/程序/gotcha 在同分竞争里胜出，episodic/历史仍可搜到；**无查询意图正则、无硬排除**。
- 可选 LLM reranker（单查询一次、并发上限 4，失败保序）；observation stream 让每场会话经其最佳 observation 给自己的会话页投一票（scope 隔离、不跨项目）。
- 所有读路径统一触发 access 强化（access_count + last_accessed_at，每页每分钟限流一次）——**被用的记忆衰减更慢**。

### 1.5 衰退层（零 LLM）
- per-tier 衰减曲线、access-weighted retention（只能让记忆活得更久，永远开启）；冷 episodic 笔记可**抽取式压缩**成持久事实（路径/错误码/决策）而非丢弃；DBSCAN 近重复合并；矛盾标记。
- forget sweep 五道工序层层设防：TTL 硬删 → 冷淘汰留墓碑 → 墓碑超期随版本祖先清除 → observations 保留期（带「不得删除某会话最后副本」「不得删未完成整合的会话」守卫）→ hook 台账按月 retention。dry-run 报数、分批事务、阻塞式 webhook 可否决删除。
- 「dream」：空闲时段用 LLM 把冷笔记簇重写成连贯页（**默认关、永不删源、要先过 recall eval 才许升为默认**）。

### 1.6 集成与分发
- 20+ harness 一方集成（CI 校验）、MCP / hooks / Agent Skills 三种接入；管理 UI 编译期 + 运行期双重 opt-in。
- 分发面：checksum 校验的 install.sh/ps1、systemd --user / launchd、AUR / RPM / Docker（多架构）/ macOS 菜单栏 app；`ai-memory setup` 展示计划并逐 agent 询问接线。

## 2. 优势

1. **零 LLM 默认路径是真正的差异化**：捕获、会话页、搜索、handoff、老化全部无需 API key——成本与隐私双优，且「用了衰减更慢」的强化机制让记忆只延寿不减寿。
2. **markdown SSOT + git**：可 grep / Obsidian / 手工编辑 / rsync；索引可重建，无二进制锁定。用户所有权做到了字面意义。
3. **跨 agent / 跨机器 / 跨团队三类跟随**：claim-once 类型化 handoff 是比「共享笔记」更强的协议语义（owner、恰好一次）。
4. **工程诚实度罕见**：实测写天花板（~700/s）写进 README、purge 语义逐条说明、全量审计日志、「先过 recall eval 才许成为默认行为」的自我约束。
5. **不可信文本治理**：单一 sanitization 入口 + 所有 LLM prompt 的 untrusted fence + 隐私边界前置——与我们「hook 文本不可信」的纪律同源但执行面更系统。
6. **集成与分发广度**：20+ harness 每个都有 CI 校验的第一方集成，安装面覆盖主流平台与打包渠道。

## 3. 劣势

1. **常驻服务复杂度转嫁给用户**：要跑 server（systemd/launchd/Docker）、管 token、开端口——对比 Repotory 的「开箱即用、零服务零配置」。单人场景这是纯开销。
2. **20+ harness 的 hook 面是持续维护债**：每家 harness 改 hook 契约都要跟。Repotory 在 importer 上吃过的格式漂移苦（codebuddy/opencode 三处漂移），他们换成了 hooks 但债是同类的——只是换了个暴露面。
3. **双 SSOT 表面的固有复杂度**：wiki 为真、DB 为派生，意味着重建路径必须永远正确；README/ARCHITECTURE 里大量篇幅在打补丁（压缩代、恢复重放、观察计数守卫、ledger 谓词）——这个选择的复杂度税集中在恢复与并发语义上。
4. **规则式摘要的天花板**：零 LLM 的会话页是模板拼装；真正「连贯的知识页」要靠 dream/consolidate 补，而那些要 LLM + 联网 + 配置。
5. **没有人在环**：auto-improve 默认**自动批准** LLM 产物进 wiki（require_approval 可开但默认不开）；先审后入不是其设计承诺——幻觉治理靠 eval 门（默认关）+ supersede 可逆，属于「可回滚」而非「不发生」。
6. **面向会话流，弱于项目知识结构**：没有项目级取证、没有编译审核工作流；「记得你上次聊了什么」强，「这个项目的架构决策与矛盾」弱。
7. Rust 单体的扩展锁定：改行为要进 Rust 代码；MCP 是唯一外挂面。

## 4. 对 Repotory 的参照

### 4.1 定位对比

| | ai-memory | Repotory |
|---|---|---|
| 记忆单元 | 会话流（hooks → 观察流 → 会话页） | 项目知识（笔记 → 编译 → 页面图） |
| SSOT | git 化 markdown 目录 | 单 SQLite（含 FTS/向量/版本/图） |
| 质量治理 | 自动批准默认 + eval 门（默认关）+ supersede 可逆 | 先审后入 + 人在环 + 版本快照 |
| 传播面 | 跨 agent / 跨机器 / 跨团队（server） | 单机本地（导出旁路 + 记忆导入） |
| 成本结构 | 零 LLM 默认 | 编译/Lint 需本地 LLM（用户自己的 LM Studio） |

### 4.2 可借鉴（按性价比排序）

1. **claim-once 类型化 handoff**：Repotory 的 handoff 是项目内笔记，没有「owner + 恰好认领一次」的跨 agent 交接语义。若做跨 agent 交接（如 v2.8.0 的 Hermes/CodeBuddy 会话导入的逆方向——把 Repotory 知识推回给 agent），这是现成协议设计。
2. **access-weighted 衰减 + 抽取式压缩（零 LLM）**：Repotory 的 wiki 会随会话页堆积老化；「被读/被链接的页衰减更慢 + 冷页抽取压缩为持久事实」是零 LLM 可抄的机制（我们已有 page_versions 做 supersede-not-delete，底座就绪）。
3. **L0/L1 字节预算 brief**：先 256B 摘要、预算加深到 500B/全文的分级打包——比我们 `aiProjectContext` 的固定截断更精细，可改造进 AskAI 上下文预算。
4. **「升默认要先过评测门」的自我约束**：与我们 abeval 门同哲学，可写进 CONTRIBUTING 作为新功能默认值变更的惯例。

### 4.3 明确不学

1. **服务化常驻**：Repotory 本地优先、零服务是定位不是缺陷。
2. **hook 面 20+ harness**：维护债换覆盖面的生意，与 importer 拉 + 单点 capture 的窄面纪律相反。
3. **markdown SSOT**：与我们「SQLite 唯一 SSOT + 单向导出」（ADR-0014 决策 2）正好互逆——他们是文件派生索引，我们是库派生导出；互逆不等于可调和，切换成本无限大。

### 4.4 一个具体的互操作机会

ai-memory 的 wiki 是**磁盘上的普通 markdown 目录**（git 化）——恰好落在 Repotory 记忆源导入器的甜点区（同 Hermes `memories/*.md` 模式：读目录、按项目匹配、幂等 upsert）。若用户将来真用它，可按「真实布局核验后再写」的既有纪律加一个 `ai-memory` 导入源（读其 `pages/` markdown + frontmatter entities，成本低于接 MCP）。**仅列为可选待触发项，不立项。**

### 4.5 生态信号

其支持矩阵里「Oh My Pi / OMP」被列为一等集成——OMP 生态在以超过预期的速度长出真实消费者。这**不改变**「等 OMP v1 再写导入器」的结论（v0.4 仍是 pre-1.0），但把「OMP 值得持续观望」的置信度调高了一档。

## 5. 结论

ai-memory 是「跨 agent 会话记忆」赛道上的强实现：**工程诚实度、零 LLM 默认路径、markdown 所有权**三点业界少见地同时成立。它的弱项（服务化开销、无人在环、会话流取向）恰好是 Repotory 的强项；它的强项（跨 agent/机器/团队、hook 捕获、老化机制）恰好是 Repotory 未做的面。对 Repotory：不构成替代与威胁，构成三样东西——**机制借鉴清单**（handoff 协议、衰减/强化、brief 分级）、**潜在导入源**（其 wiki 目录）、以及**反面印证**（先审后入与库内 SSOT 是有价值的差异点，值得继续守住）。
