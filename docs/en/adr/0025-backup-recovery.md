## Background

The 2026-10-14 real-database incident: `repotory.db` suffered page-level corruption on the internal disk (101 invalid page numbers), 75 notes dropped to 22, and `.recover` saved what could be saved. The root cause was that **the data lived on exactly one disk with no usable external copy**.

Two things happened afterwards. The user enabled Time Machine daily backups (10-16), but the backup drive has never been connected — TM only writes while its disk is attached, so "daily" does not hold while the disk is detached, and **to this day not a single TM backup containing repotory data exists**. The user then explicitly deferred plugging the drive in (2026-10-18, with a fair reason: almost nobody buys a dedicated external drive for backups any more) and reframed the problem in modern terms — "how does MySQL solve this? Is there something better with Docker?"

The modern database industry's answer (the MySQL family): the backup unit is not "a user copying files by hand" but **self-produced snapshots plus change logs**, and the destination is **object storage** (off-machine, eleven nines, pennies a month), fully automated. SQLite and InnoDB are both WAL architectures, so the answer transfers wholesale — the SQLite ecosystem's counterpart is Litestream-style WAL streaming. Docker's role in that world is merely "a convenient container to run the mover in"; it does not itself solve durability (a same-host named volume is still the same internal disk).

This ADR splits that answer into three tiers shaped for Repotory, and lands the only tier that requires nothing from the user and touches no privacy gate: L1.

## Decisions

**Decision 1: L1 daily local snapshot, ON by default (landed this round).** Run `VACUUM INTO` on the live connection into `<data dir>/backups/repotory-YYYY-MM-DD.db`. The load-bearing points:

- **The date is the idempotency key.** After the first successful snapshot of a day, every same-day retry is a no-op. "Daily backup" therefore means "the first app open of the day" on desktop and "the first hourly tick of the day" on the headless server — no timer arithmetic to get wrong, and the desktop usage rhythm naturally is the backup rhythm.
- **Rotation** keeps 14 snapshots by default (`backup_retain`) and only ever touches files with the `repotory-*.db` prefix — anything else the user drops into that directory is never deleted.
- **Why default ON:** a snapshot is a local file write with zero outbound traffic and no privacy exposure. "Default off" is reserved for switches that send content outward (`semantic_search` / `auto_import` and their family); backups are not that family. Once the user sets `backup_enabled=0`, both the ticker and manual runs get the same explicit refusal (no silent no-op — the same rule `StartLintJob` follows).
- **Permissions 0600:** the snapshot carries the full dataset — the same discipline as the data directory.
- One snapshot attempt at startup plus hourly retries, all through `bgGo` so Shutdown tracks them; a failed snapshot is logged, never escalated into an app failure.

**Decision 2: the recovery path is "copy one file back".** A snapshot is a complete, standalone SQLite file; restoring is swapping the file — the shortest, least error-prone path, and the direct continuation of the manual restore-point flow validated after the incident. The promotion criteria require rehearsing it once on a real machine.

**Decision 3: L2 cloud push is opt-in; this ADR shapes it but does not implement it.** Two equivalent forms: Litestream-style WAL streaming (near-PITR) or scheduled upload of L1 snapshots to an S3-compatible object store. The privacy-gate discipline is exactly M3's: **no credentials configured = zero outbound, default OFF**, with the same "only when you actively configure…" wording. The Docker deployment tier (NAS/homelab users) is a documented compose file — `repotory-server` container + data volume + a litestream sidecar; the desktop experience does not gain a Docker dependency.

> **Implementation note (2026-10-19, form two)**: the chosen shape is "scheduled upload of the L1 snapshot" rather than Litestream — the snapshot is already produced by L1 and its daily filename is the idempotency key, so uploading just moves an existing artifact and does not import a second recovery semantics for stream archiving. The S3 client is **minio-go** (pure Go, zero CGO, works against S3/R2/MinIO/B2 alike); the client is constructed per upload and dropped afterwards, so credentials never linger in memory. All six `backup_remote_{enabled,endpoint,bucket,prefix,access_key,secret_key}` keys default to empty, and **when enabled != 1 or any required key is empty the dialer is never even constructed** (`TestRemoteBackupOffByDefault` / `TestRemoteBackupMissingCredsStaysLocal` pin "zero egress" on behaviour, not intention). The object name is the snapshot filename (`<prefix>/repotory-YYYY-MM-DD.db`); an existing object skips the upload (per-day idempotence) and a failed upload is only logged — the hourly ticker retries for free. A regression test pins the red line: **the object-key regexp admits only snapshot filenames; the live database and its WAL/SHM sidecars can never have an object name**. RunBackupNow's return contract is unchanged (still the local path) — the push is a pure side path. The settings page's "Database backup" group offers the switch plus a five-field form; the manual (`docs/data-management.md`, zh/en) gains L1/L2/Docker sections.

**Decision 4: red line — a live database never lives inside a cloud-sync folder.** File-level sync tools (iCloud Drive, OneDrive, rclone mount…) syncing an actively-written SQLite file are a well-known corruption source, and the 10-14 interference suspect (15 `.fuse_hidden*` files in the data directory) points exactly at that family. Cloud-ifying is allowed in exactly two forms: syncing **static snapshot files the database itself produced**, or **streaming the WAL** — never letting a sync tool touch the live file.

**Decision 5: Time Machine is neither replaced nor excluded.** TM backs the whole data directory (import sources, logs, the snapshot directory itself); L1 backs the structured single file, readable on any machine. While the drive stays unplugged, L1 fills the "zero backups" vacuum; if the user plugs it in, the two stack.

**Decision 6: L3 off-disk copy = opt-in, one key; a copy is verified before it counts; and the product must answer "is this the same disk as the live database?".** L1's snapshot sits on the same disk as the live database — the 10-14 incident is exactly the price of "the data lives on one disk". L2's cloud push is the right answer for a server, but it demands an object store plus two credentials; somebody who plugged in an external drive should not have to stand up an object store first to get a second copy. The shape is a single key, `backup_copy_dir`:

- **Empty = completely off**: no directory is created, no file is written, nothing is probed (the same discipline as L1/L2).
- **Non-empty = the snapshot is copied over** once the daily local snapshot exists. The target directory is the user's choice: an external drive, a NAS mount, or an existing synced folder. What gets copied is a **static snapshot file the database itself produced**, never the live database — inside what Decision 4 allows, and a sync tool still never touches the live file.
- **A copy is verified**: before it is published, the copy must pass `VerifySnapshot` ("is this a database that opens?"), and an unverifiable copy is never published. The reason is L1's: a copy nobody can restore is worse than no copy, because it lets you believe "I have a backup".
- **The date is the idempotency key**: an existing readable copy of the day is skipped, so the hourly ticker does real work once a day.
- **The target directory belongs to the user**: rotation only ever deletes files whose WHOLE name matches `repotory-YYYY-MM-DD.db` — a file that merely looks like ours (`repotory-notes.db`) is never touched; the copy is 0600; it is written to a temp file in the destination directory → `fsync` → verified → published by an atomic rename (a half-written copy is worse than no copy).
- **Runs in the background with a 5-minute cap**: the target is usually a mount the user controls, and a stale network mount must not wedge the backup ticker — the local snapshot has already succeeded by then, so only the copy is lost.
- **The one thing L3 adds: the same-disk check.** A target on the same disk as the live database means that "backup" is just another copy of the thing that failed — and the user cannot see it by looking at the path: "a backup folder one folder away" looks exactly like "a backup folder on an external drive". So the settings page offers `CheckBackupCopyTarget`: does the directory exist? can it be written to? **is it the same disk as the live database?** A same-disk target is an **advice, not a refusal** — the copy is still made, because the user may well want a "protects against accidental deletion" copy; but the sentence has to be said out loud.
- **On Windows, "cannot tell" is the answer**: that platform cannot supply a reliable volume serial number, so "is it another disk" answers "cannot determine" — a wrong reassurance (reporting it as a different disk) is worse than none, because it extinguishes the very reason this check exists.

## Costs

- **Disk**: ~5MB × 14 ≈ 70MB ceiling — negligible at this scale; rotation depth is the first knob to turn when the database grows.
- **Snapshots are full copies, not incremental**: once the database grows, daily full copies waste obviously — switching to Litestream-style incrementals is a future decision outside this ADR.
- **No frontend surface yet**: the `RunBackupNow` binding is registered (a settings-page button and scripts can call it), but the settings UI is not wired — deferred until the first real signal. ~~*(superseded 2026-10-19: settings → operations → database backup now carries the L1 controls plus the L2 remote form; kept here struck through because the ZH twin recorded the cost differently)***
- **Two engineering compromises** (see "Implementation corrections"): the snapshot permission needs an explicit chmod, and the two config keys register from the feature file because of a write-guard misread.
- **L3 adds one more full copy**: it occupies space in a directory the user picked, is off by default, and is the user's call.
- **The same-disk check is unavailable on Windows**: `DeviceID` can only answer "cannot determine" there. Users on that platform never get the "is this another disk?" sentence — that is the honest answer, not a hole to be papered over with a guess.

## Implementation corrections

1. **`VACUUM INTO` writes with the process umask (0644 observed), not the data directory's 0600** — the snapshot carries the full dataset, so an explicit `chmod 0600` follows success, and the failure path removes the half-written file (a partial snapshot is worse than none).
2. **The write guard misreads `config.go`'s pre-existing `ai_chat_api_key（布尔开关）` allow-list entry (a boolean flag, not a credential) as a credential literal** — any rewrite of that file is refused. The two new keys therefore register themselves in `backup.go` via `init()` — same package, same map, feature and registration in one file, which is arguably more cohesive; `config.go` is untouched byte for byte. Centralising them back into `config.go` later needs the user to approve that specific write.
3. Tests inject the snapshot directory through the unexported `Service.backupDir` field, making it impossible for a test to write into the real user data directory.
4. **`UpdateConfig`'s numeric guard locked every free-text key out**: `backup_copy_dir` and L2's five `backup_remote_*` fields registered in `allowedConfigKeys` (writable) but not in `stringConfigKeys` (the table that exempts a key from the numeric check), so saving them failed with "config value must be a number". The damage is not small: **L2's settings form could not save a single field** from the day it landed on 2026-10-19 — all five raised the error. Nobody noticed because L2's existing tests write the config table directly (`db.SetConfig`), bypassing `UpdateConfig`, the path the UI actually takes. The fix: both features register in `stringConfigKeys` from their own `init()`, plus a regression test that goes **through `UpdateConfig`** — a test must cover the button the user really presses, not an internal shortcut.
5. **L3 reports its verdict as a machine-readable `code`, not a sentence**: the backend does not know the user's language, and a Chinese sentence in the payload puts Chinese into the English UI (against this repo's i18n discipline). `CheckBackupCopyTarget` therefore returns `code` + `blocking`, and the frontend maps the code to its own translation; `blocking` separates "a copy could never land there" from "the copy works but sits on the same disk as the live database (advice only)" — the latter is not a refusal: the user may want a copy that protects against accidental deletion.
6. **"The parent directory does not exist" is not a failure**: `CopyBackupTo` uses `MkdirAll`, so missing parents are created too — deciding whether the directory CAN be created therefore depends on the nearest EXISTING ancestor being writable, not on the immediate parent. This also covers the macOS trap: `/Volumes/<name>` is created by the OS when a disk is mounted, and it is an ordinary directory on the root volume when the disk is not mounted — the same-disk check speaks up there and says "you thought this was another disk, you were writing to the system disk".
